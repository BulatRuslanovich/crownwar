# Аудит архитектуры: готовность к мультиплееру

Состояние на момент завершения одиночной версии (этап 6). Сетевой слой не реализован; документ
описывает, что уже готово, что мешает и какой минимальный путь к сетевой игре.

## Итог

Архитектура подходит для **авторитарного сервера**: правила живут в чистой C#-библиотеке
`Lordsio.Sim`, мир меняется только через команды, у зданий и юнитов стабильные числовые id,
отображение уже интерполирует позиции между тиками. Рекомендуемая модель — сервер считает
симуляцию, клиенты присылают команды и получают снимки состояния и события.

Lockstep (все считают одно и то же) возможен только с оговорками — см. «Детерминизм».

## 1. Как игрок и бот отправляют команды

- Единственная точка входа — `Simulation.Issue(Command)`. Команды — неизменяемые `record`:
  `MoveCommand`, `AttackCommand`, `RecruitCommand`, `BuildCommand` (`sim/Lordsio.Sim/Core/Commands.cs`).
- Команды ставятся в очередь и применяются в начале следующего тика (20 Гц), а не в момент вызова.
- Игрок (`SelectionController`, `BuildPlacement`, `Hud`) и боты (`BotBrain`) пользуются одним и тем же путём.
  Бот читает только публичное состояние и не имеет обходных путей (проверено тестом
  `BotsOnlyChangeTheWorldThroughCommands`).

**Готово для сети:** команды маленькие и легко сериализуются (id юнитов, точка, тип, клетка).

**Нужно добавить:**
- номер тика, к которому команда относится (клиент присылает команду «на тик T», сервер применяет на T+задержка);
- сериализацию (`MemoryPack`/`System.Text.Json` или ручной бинарный формат).

## 2. Как меняется состояние мира

- Только внутри `Simulation.Step()`: команды → экономика → стройка и найм → поведение юнитов и башен →
  движение → снаряды → расталкивание → проверка застревания → удаление погибших → выбывание и победа.
- Наружу состояние доступно только для чтения (`Units`, `Buildings`, `Factions`, `Deposits`, `Projectiles`).
- Всё, что видно игроку, но не влияет на правила (выделение, камера, эффекты, звук, анимации, предупреждения),
  живёт на стороне Godot и строится по событиям (`TakeEvents()`).

## 3. Централизованная проверка команд

Все проверки уже в симуляции, интерфейс их только показывает:

| Команда | Проверяется |
|---|---|
| Move / Attack | юниты принадлежат фракции и живы; цель существует, жива и вражеская |
| Recruit | здание своё и достроено, тип нанимается здесь, очередь, лимит армии, золото (`CanRecruit`) |
| Build | тип строится, границы, местность, занятость, месторождение, свои войска рядом, золото (`CanBuild`) |
| Любая | фракция не выбыла |

**Главный пробел:** `Command.FactionId` задаёт отправитель. В одном процессе это нормально, но сервер
**обязан** проставлять фракцию по соединению и не доверять полю из сообщения клиента. Также нужны
ограничение частоты команд и лимит размера списков id.

## 4. Какие данные синхронизировать

Клиенту для отрисовки нужно:

| Данные | Поля | Частота |
|---|---|---|
| Юниты | id, тип, фракция, позиция, здоровье, состояние (идёт / бьёт), направление | каждый снимок |
| Здания | id, тип, фракция, клетка, здоровье, ход стройки, очередь найма | при изменении |
| Снаряды | позиция, цель | каждый снимок (или выводить на клиенте из `ProjectileFired`) |
| Фракции | золото, доход, лимит, численность | **только своей фракции** |
| Месторождения | id, занятость | при изменении |
| События | `AttackLanded`, `UnitDied`, `BuildingDestroyed`, … | по мере появления |

Оценка трафика: 200 юнитов × ~16 байт × 10 снимков/с ≈ 32 КБ/с на клиента без сжатия;
с дельтами и квантованием позиций — в разы меньше. Клиент уже интерполирует между тиками
(`InterpolationAlpha`), поэтому 10 снимков в секунду при 20 тиках сервера достаточно.

События нужно фильтровать по получателю: `RecruitRejected`, `BuildRejected`, экономика — только владельцу.

## 5. Авторитет сервера над боем, экономикой и территорией

- Урон, смерть, снаряды (`CombatSystem`), золото (`Treasury`), стройка и выбывание (`Simulation.Buildings`)
  целиком в симуляции. Клиенту не нужно ничего из этого считать — ему хватит снимков.
- `CanBuild` удобно запускать и на клиенте для подсветки призрака здания, но решение остаётся за сервером
  (так уже и сделано: кнопка всегда отправляет команду, отказ приходит событием).

## 6. Что мешает сейчас

1. **Отображение привязано к классу `Simulation`.** 21 Godot-скрипт читает `match.Sim` напрямую.
   Для клиента нужен слой «модели мира» (интерфейс или классы-реплики, заполняемые из снимков),
   который реализуют и локальная `Simulation`, и сетевая реплика. Это главный рефакторинг.
2. **`Unit.Target` и `Projectile.Target` — ссылки на объекты**, а не id. Для снимков нужно передавать id.
3. **Нет сериализации состояния** — нужен полный снимок для подключения и переподключения.
4. **Нет тумана войны.** Сейчас каждый видит всё; по сети это значит, что клиент получает всю карту
   (подсказка для читов). Туман — отдельная задача и правило игры.
5. **Боты живут в `MatchController`** клиента. В сети они должны работать на сервере (уже возможно:
   `BotBrain` не зависит от Godot).
6. **Правила и карта читаются из файлов** — сервер должен проверять совпадение версий (хеш `rules.json` и карты).

## 7. Детерминизм (если рассматривать lockstep)

- Случайность только из заданного seed (`MatchSetup.Seed`, seed ботов). ✓
- Порядок обхода коллекций, влияющих на результат, детерминирован (списки, `SortedDictionary`,
  `PriorityQueue` с одинаковой последовательностью операций; `HashSet` только для проверок `Contains`). ✓
- Арифметика на `float`/`MathF`. На одной сборке и одной архитектуре (x64) результаты совпадают,
  но между x64 и ARM, разными версиями .NET или при FMA-оптимизациях могут разойтись.
  Для надёжного lockstep пришлось бы перейти на фиксированную точку — это большая переделка.

**Вывод:** lockstep не рекомендуется; авторитарный сервер не требует детерминизма между машинами.

## 8. Минимальный путь к сетевой игре

1. Выделить интерфейс модели мира для отображения; локальная `Simulation` реализует его без изменений поведения.
2. Заменить ссылки на цели id в публичном состоянии.
3. Добавить сериализацию команд и снимков (полный + дельта) и фильтрацию событий по фракции.
4. Сервер: `Simulation` + `BotBrain` + проставление `FactionId` по соединению + лимиты команд.
5. Клиент: реплика модели мира из снимков, интерполяция (уже есть), отправка команд с номером тика.
6. Транспорт: Godot `ENetMultiplayerPeer` или собственный UDP/WebSocket; сетевые зависимости не нужны до этого шага.
